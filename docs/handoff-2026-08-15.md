## BUG #1 — RESOLVED: owner camera pitch pinned to ±90

**Root cause (confirmed host-side, same evening): Hyper-V synthetic mouse in absolute
coordinate mode fighting Minecraft's Raw Input.** `Microsoft Synthetic Mouse` with
`AbsoluteCoordinates = True` + `rawMouseInput:true` + GLFW 3.4.1's relative-motion
capture: absolute coordinates get misread as relative deltas, so a tiny move becomes a
huge pitch delta that slams into the ±90 clamp. Not the mod — the in-VM investigation
below independently ruled out every Ensoul code path, and the host-side one found no
mouse/yaw/pitch hooks either (the two MouseHandlerMixins in the log are stock Fabric API).

**UPDATE: Raw Input OFF did NOT fix it.** That kills the *option* as the lever but not
the diagnosis: with an absolute-coordinate synthetic mouse, BOTH of Minecraft's input
paths are corrupted — raw WM_INPUT deltas AND the cursor-warp capture that GLFW's
disabled-cursor mode uses when raw input is off (VMConnect keeps injecting absolute
positions; the game keeps warping the cursor to window center; every injected position
reads as a huge jump). This is the well-known "FPS mouse-look does not work through
VMConnect" problem, and no options.txt setting escapes it.

Discriminator that needs no restart: if the cursor moves NORMALLY inside menus/the
inventory (absolute mode) while captured look is broken, that is the capture-mode
conflict signature, full stop.

**Resolution path: run the client on the HOST** (this handoff's build steps). If pitch
is fine there — expected — close as environment. If it somehow reproduces on the host,
fall back to a debug mixin logging every `LocalPlayer#setXRot` write with a stack
trace. In-VM play would need a proper relative-mouse streaming layer (Parsec/Moonlight
class), which is not worth building tonight. The OpenAL failure is the same category —
VM environment, not code. For the filmed competition, the client belongs on the host
regardless: VMConnect input injection and frame readback each add ~a frame of latency.

The investigation record below is kept for reference — it is a map of everything that
does NOT touch the camera, useful the next time an input oddity appears.

### Original investigation (kept for reference)

Symptom (confirmed via F3 screenshots, singleplayer, Fabric dev client IN THE VM):
- Owner ("Dev") pitch reads exactly `90.0` / `-90.0`, flips sign with vertical mouse
  motion, cannot rest in between. Yaw fully free.
- Started at/near first companion summon (19:14); **SURVIVES companion despawn**
  ("gone for good" dismiss at 19:33, pitch still pinned) — so it is NOT the
  companion's look/autonomy/reflex drivers.

Ruled out by direct reading (do not re-tread):
- All four mixins: MenuDataSlotsAccessor, MixinServerCommonPacketListener (drops
  outbound to FakeConnection — verified muzzled), MixinMinecraft (log-only),
  MixinAbstractClientPlayer (getSkin only).
- Fake-connection packet leak to the real client (dropped at listener level).
- Every InputDriver/LookController/lookAt call site — all typed to the companion.
- ClientControl (pure state mirror), tonight's full diff (zero camera/mouse/rotation
  matches), options.txt (stock defaults).

Prime suspect after all that: **the VM itself.** `rawMouseInput:true` + a VM's
absolute-pointer mouse virtualization is a classic cause of exactly this
(one axis pinned at clamp, other fine). Also consistent: `Failed to open OpenAL
device` (no VM audio), 2560x1511 scaled display.

Decisive experiments, in order of cheapness:
1. In-game: Options → Controls → Mouse Settings → Raw Input OFF (instant, no restart).
2. Relog without summoning (world is companion-free now) — does pitch work?
3. Run the client on the HOST (this handoff's purpose). If pitch is fine on the host,
   close the bug as "VM mouse virtualization", note it in docs, move on.
4. Only if it reproduces on the host: add a debug mixin logging every
   `LocalPlayer#setXRot` write with a stack trace, summon once, read the trace.
